## 一、根因链

### ① 网关密钥额度耗尽（用户报的 403）
TokenDance 网关 key `sk-dd08a5…` 对所有请求返回 `403 api_key_quota_exceeded`，**文本与图像同时不可用**。

**处置**：整体切换到阿里云百炼官方端点
`BAILIAN_BASE_URL=https://dashscope.aliyuncs.com/compatible-mode/v1`，key 换 `sk-d57ef2…`。
实测官方端点能力（切换前逐个验证）：

| 能力 | 结论 |
|---|---|
| 文本 `qwen3.7-max` | ✅ 200 |
| **function calling** | ✅ 正常返回 `tool_calls`（Agent 主循环依赖） |
| **视觉 `qwen3-vl-plus`** | ✅ 真实读图（旧网关无 VL 模型，商品理解原本只能走纯文本） |
| 出图 `wan2.7-image` | ✅ 同步返回图片 URL |

> ★ **出图必须走万相原生端点**。官方兼容模式**没有** `/images/generations`（404），
> 而经 chat 通道出图会返回 **HTTP 200 但 message 里既无 content 也无 image** —— 静默失败，最难发现。

### ② 云端缺少万相密钥 → 云端无图可出
线上环境变量里**没有** `QIANAN_DASHSCOPE_API_KEY`，因此云端出图主链路是关闭的，
所有出图都压在已死的网关链路上。**已补入** `cloudbase/cloudbaserc.json` 并由部署脚本物化注入。

### ③ 审核—修订死循环（烧光预算，出图 0 张）
`agents/review.py` 把语义审核结果**一律标为 `severity="error"`**，而 system prompt 规定「有 error 必须调用 revise_listing」。
但审核 prompt 要找的「无事实支撑的夸大」**没有收敛点**——每轮改掉一批，文案又会带出新的具体表述被判同类问题：

```
review_listing[amazon] -> warn  →  revise_listing[amazon]  →  review … （11 轮）
→ 耗尽 300s 墙钟预算，图片 0 张、视频 0 个，最终 partial
```

**修法**：
- 审核输出增加 `type` 分级：`contradiction`（与事实档案直接矛盾）= **error**；
  `unsupported`（档案没写、证据不足）= **warn**；缺失/未知 type **fail-safe 为 warn**。
- 新增 `MAX_REVISE_ROUNDS = 3` 硬上限。
- system prompt 明示「warn 不必修、预算优先保证每个平台都有主图并完成交付」。

### ④ 交付闸门与平台规则互相打架（永远交付不了）
交付闸门对**所有平台**要求 `bullets` 非空，但规则文件写得很清楚：

| 平台 | bullets 规则 |
|---|---|
| amazon | `count: 5` |
| shopee / lazada / aliexpress / tiktokshop | **`count: 0, style: "none"`**（无独立五点，卖点融入描述段落） |

文案 Agent 的提示词照规则让非 Amazon 平台返回空数组 → Shopee 永远被判「缺五点描述」
→ 交付被无限拒绝 → Agent 反复重新生成文案直到 25 轮上限，**5 个平台一个都交付不了**。

**修法**：闸门新增 `rules_map` 参数，按平台规则判断（仅 `count > 0` 才要求 bullets）；
**不传时保持旧严格行为**，避免静默放松判定。

## 二、性能修复（出图单步 373s → 22.6s）

| 问题 | 修复 |
|---|---|
| litterbox 图床已对数据中心 IP 返回 403/412，转存 **100% 失败**却按 `90s × 3 次` 傻等 | 进程级**熔断** + 超时 `90s → 15s` + 新增 `QIANAN_IMAGE_PERSIST=0` **默认关闭转存**（直接用万相 OSS URL） |

| `CHAT_DEADLINE_S=300` 但云函数 `timeout=120` → 121s 被硬切 | 云函数提至 **900s**（SCF 上限），Agent 预算提至 **420s** |

## 三、部署脚本修复（曾静默丢失配置 ★）

`tcb fn code update` 完成后函数会短暂处于 **Updating** 状态，紧接着执行的 `config update` 会被
`UpdateFunctionConfiguration` 拒绝（"当前函数处于 Updating 状态"）——
**结果是代码更新成功、环境变量没更新**，表现为「改了 key 但线上还在用旧的」。

已在 `cloudbase/deploy.sh` 内置：**轮询等待状态回落 → 3 次重试 → 失败即报错退出**（不再静默通过）。
另新增 `--api-only` 开关：只更新后端云函数，跳过前端构建与托管部署。
