# 千岸 QianAn · PRD v2

> 状态：Draft  
> 日期：2026-09-05  
> 产品主张：**从选品到上架，一键完成**  
> 本文档取代 `PRD-v1.md` 作为当前产品定义；旧文档仅保留为决策历史。

## 1. 产品定义

千岸是一名跨境新品上新 Agent。它帮助卖家发现值得销售的商品，整理并补齐商品资料，自动生成主图、详情页和多语言 Listing，按照不同市场与平台规则完成检查、修复和后台发布，将传统数天的新品上架流程压缩至分钟级。

### 1.1 用户购买的结果

用户购买的不是“AI 生成了多少内容”，而是：

> 一个真实商品经过信息确认、平台准入、草稿生成、合规检查和人工确认后，成功提交至目标平台；如果失败，能够明确知道原因并继续修复。

### 1.2 产品原则

1. **事实优先**：不确定的商品信息留空或请用户确认，不得为了内容完整而编造。
2. **结论优先**：每一阶段先告诉用户“能不能继续、缺什么、下一步做什么”。
3. **人审可控**：对外发布前必须有明确的用户确认闸口。
4. **过程可追溯**：字段来源、草稿版本、检查结果、发布动作和平台回执必须可查。
5. **失败可恢复**：平台拒绝不是流程终点，必须能回到具体问题项修复并重新发布。

## 2. 问题与 Why Now

### 2.1 核心用户

有稳定货源、需要持续上新的中小跨境卖家和运营团队，尤其是没有专职翻译、设计和合规人员的团队。

### 2.2 用户任务

> 当我准备上一个新品时，我希望 AI 帮我判断它是否值得卖、还缺什么资料，并完成准确、合规的平台内容和后台发布，让我不需要在多个工具和后台之间反复切换。

### 2.3 现有方案的断点

| 断点 | 当前表现 | 对用户的影响 |
|---|---|---|
| 输入过早结束 | 一张图或一句话即可生成 | 缺失信息被模型补写，上架风险不可控 |
| 没有商品事实层 | 用户无法确认信息来源 | 不知道哪些内容可信 |
| 检查结论模糊 | “通过”与缺失项同时出现 | 不知道当前是否真的可发布 |
| 生成与发布脱节 | 无发布版本和闸口 | 无法确认最终向平台提交了什么 |
| 失败无回路 | 失败只展示错误或停在日志 | 用户仍需人工定位和重复操作 |

### 2.4 为什么现在做

现有系统已拥有规则引擎、多平台生成、合规检查、发布执行器和轨迹数据。当前的主要缺口不是更多 AI 能力，而是把已有能力组织成一条用户能完成的工作流。

## 3. 成功指标

### 3.1 北极星指标

**成功提交至目标平台的 SKU 数量。**

演示环境中，“成功提交”以 mock 卖家后台返回 `listing_id` 和可查回执为准，不用“内容已生成”替代。

### 3.2 MVP 验收指标

| 指标 | MVP 目标 | 统计口径 |
|---|---:|---|
| 从建项到首次可发布时间 | ≤ 5 分钟 | 从创建项目到没有阻断项 |
| 首次发布成功率 | ≥ 80% | 成功返回 listing_id / 发布尝试数 |
| 无依据内容出现率 | 0 | 未经确认事实进入已发布内容的比例 |
| 阻断项修复闭环率 | 100% | 每个阻断项都有定位、修复和复检动作 |
| 发布可追溯率 | 100% | 每次发布都关联草稿版本、执行步骤和平台回执 |

## 4. 产品范围

### 4.1 MVP 范围内

- 单个 SKU 上新项目。
- 已有商品入口：图片 + 文字资料。
- Amazon US 作为默认深度演示平台。
- 商品事实提取、缺失项补充和人工确认。
- 平台准入与发布前合规诊断。
- Listing 和主图草稿生成、编辑、重新生成与复检。
- 发布前人工确认闸口。
- mock 卖家后台发布、回执、失败修复和重试。
- 结构化执行记录和必要截图。

### 4.2 MVP 范围外

- 真实平台的无人值守自动提交。
- 五平台同时深度支持。
- 多 SKU 批量审阅和批量发布。
- 基于真实经营数据的转化优化和自动改写。
- Agent 自主安装技能或自动应用进化提案。
- 完整的多用户、权限和租户体系。

## 5. 核心产品对象

### 5.1 SKU 上新项目

“SKU 上新项目”取代“生成任务”成为用户可见的主对象。一个项目至少包含：

- 商品事实档案与字段来源。
- 目标市场、平台和站点。
- 平台草稿及版本。
- 阻断项、警告和优化建议。
- 用户确认记录。
- 发布工作和平台回执。
- 失败原因、修复操作和重试历史。

### 5.2 商品事实

每个事实字段必须包含：

```text
key / label / value / source / confidence / confirmation_status / evidence
```

`source` 取值：`user | document | image | external | inferred`。  
`confirmation_status` 取值：`confirmed | needs_confirmation | missing | rejected`。

**强约束**：`inferred` 且未确认的事实不得进入可发布草稿。

### 5.3 发布版本

每次发布绑定一个不可变的草稿快照，包含文案、属性、图片、定价、库存、规则版本和确认记录。后续编辑必须生成新版本，不得覆盖已发布快照。


## 7. 信息架构

### 7.1 一级导航

- **上新项目**：默认首页，展示所有 SKU 项目与下一步。
- **选品机会**：按市场、类目、成本和利润筛选候选品。
- **商品库**：复用已确认的商品事实和素材。
- **发布中心**：查看发布任务、回执、失败与重试。
- **规则中心**：查看平台规则来源、版本和适用范围。

Agent Trace、技能商店、连接器和进化提案下沉到“技术详情 / 设置”，不作为卖家主旅程。

### 7.2 项目详情页

顶部固定显示：

- 项目名称和 SKU。
- 目标平台 / 站点。
- 当前状态。
- 阻断项数量。
- 唯一主操作（例如“补齐 3 项信息”）。

项目内部使用四个业务 Tab：

1. 商品事实。
2. 平台草稿。
3. 发布检查。
4. 发布记录。

## 8. 状态机

| 状态 | 系统结论 | 主操作 |
|---|---|---|
| `draft` | 项目刚创建 | 上传或粘贴商品资料 |
| `facts_incomplete` | 商品事实不足 | 补齐 N 项信息 |
| `facts_review` | AI 已提取，等待确认 | 审核商品档案 |
| `market_selection` | 尚未确定发布目标 | 选择市场与平台 |
| `diagnosing` | 正在计算准入与风险 | 查看实时进展 |
| `blocked` | 存在发布阻断项 | 处理 N 个阻断项 |
| `generating` | 正在生成草稿 | 查看实时进展 |
| `review_required` | 草稿已完成 | 审核草稿 |
| `publish_ready` | 已无阻断项 | 确认并发布 |
| `publishing` | 正在向平台提交 | 查看发布步骤 |
| `published` | 平台已接受 | 查看平台回执 |
| `publish_failed` | 发布失败 | 修复问题并重试 |

**规则**：页面上的主操作必须由当前状态决定，不同时展示多个互相竞争的主按钮。

## 9. 功能需求

### F1 · 项目创建与商品资料导入（P0）

**用户需求**：我已经有一个商品，希望用最少操作建立上新项目。

**交互**：

- 支持上传商品图片，粘贴商品名称和现有资料。
- 用户必须选择目标市场、平台和站点；类目可由 AI 推荐，但必须确认。
- 主按钮文案为“分析商品资料”，不直接承诺已生成可上架内容。

**验收标准**：

- Given 用户仅上传图片，When 开始分析，Then 系统创建项目并把不能确认的字段标记为缺失，不自行补写。
- Given 用户未选择平台站点，When 尝试继续，Then 系统阻止并说明需要该信息的原因。

### F2 · 商品事实提取与确认（P0）

**用户需求**：我需要知道系统理解了什么，哪些信息还不可信。

**交互**：

- 按“已确认 / 待确认 / 缺失”分组展示商品字段。
- 展示字段来源和证据，但不将模型概率当作业务事实。
- 允许用户批量确认高信心且来源明确的字段，其余逐项补充。
- 顶部始终显示完整度和下一步，例如“已确认 17/23，还需补充 4 项”。

**验收标准**：

- Given 字段来自 AI 推断，When 用户未确认，Then 该字段不得进入可发布草稿。
- Given 用户否决某个字段，When 保存，Then 该值不再被后续生成任务恢复。

### F3 · 准入与商业诊断（P0）

**用户需求**：在生成素材前，我需要知道这个商品是否适合目标市场与平台。

**输出**：

- 平台准入状态：可上架 / 补充后可上架 / 暂不建议上架。
- 必填属性缺失、认证要求、限售风险和图片规范。
- 已提供成本与物流信息时，展示参考价格带、预估利润和关键假设。

**验收标准**：

- Given Amazon US 任务，When 执行准入诊断，Then 不调用仅适用于欧盟的 GPSR 工具。
- Given 存在认证或必填字段阻断，When 用户查看结果，Then 页面不显示“合规通过”。

### F4 · 平台草稿生成与审核（P0）

**用户需求**：我希望快速得到可编辑的平台草稿，并知道每段内容的依据。

**交互**：

- 标题、卖点、描述、属性和图片均可编辑。
- 每个生成字段可查看所引用的商品事实。
- 用户可以接受、修改、重新生成或标记不准确。
- 重新生成时选择原因：与商品不符、太夸张、不够本地化、未突出核心卖点、自定义要求。
- 编辑后执行确定性规则复检，不需要重新运行整条 AI 流水线。

**验收标准**：

- Given 生成内容引用了未确认事实，When 进入审核，Then 对应字段被标记为阻断项。
- Given 用户修改标题导致超长，When 字段失焦或手动校验，Then 页面就地显示规则、当前长度和修复建议。

### F5 · 发布前检查与确认闸口（P0）

**用户需求**：我需要一个明确结论，知道当前版本是否可以向平台提交。

**检查级别**：

- **阻断**：不解决不能发布。
- **警告**：允许发布，但需要用户明确知情。
- **建议**：不影响发布，仅用于优化。

**发布摘要**：平台与站点、草稿版本、价格、库存、图片、已确认事实数、阻断数和警告数。

**验收标准**：

- Given 存在任意阻断项，When 用户进入发布检查，Then 发布按钮禁用且主操作变为“处理 N 个阻断项”。
- Given 只存在警告或建议，When 用户确认后，Then 可创建发布版本。

### F6 · 发布执行、回执与失败重试（P0）

**用户需求**：我需要知道平台已经接收了什么，以及失败后如何继续。

**交互**：

- 发布时以业务动作展示进度：连接卖家后台、创建草稿、填写信息、上传图片、提交审核。
- 成功后展示平台商品 ID、Seller SKU、提交时间、回执和目标链接。
- 失败时将平台错误映射到具体字段或素材，提供修复动作。
- 修改后自动复检，并创建新的发布版本重试。

**验收标准**：

- Given 平台返回成功，When 发布完成，Then 项目进入 `published` 且保存可查的回执。
- Given 平台拒绝某个属性，When 发布失败，Then 项目进入 `publish_failed`，页面聚焦问题字段并提供“修复并重试”。

### F7 · AI 选品入口（P1）

**用户需求**：当我没有确定商品时，希望从市场、成本和风险角度得到可解释的候选品。

**输入**：目标市场、类目、成本区间、货源能力和目标利润率。

**输出**：候选商品、数据来源、需求信号、竞争强度、价格带、预估利润、准入风险和主要假设。

**约束**：无法证明与跨境商品销售相关的通用热搜不得作为选品证据。

**转换动作**：“选择该商品并创建上新项目”，后续仍进入商品事实确认，不跳过审核。

## 10. Agent 与规则边界

### 10.1 工具路由

工具不由模型在全局目录中任意选择。系统必须先根据以下维度生成工具白名单：

```text
平台 × 站点 × 市场 × 类目 × 商品风险标签
```

例如 Amazon US 任务不应获得仅面向欧盟的 GPSR 工具。

### 10.2 规则结论

统一为三级：

| 级别 | 含义 | 是否允许发布 |
|---|---|---|
| `blocker` | 必填、准入或高风险问题 | 否 |
| `warning` | 需要用户知情确认 | 确认后可以 |
| `suggestion` | 优化建议 | 是 |

页面不使用“通过率”代替发布结论。

### 10.3 轨迹展示

默认展示用户可理解的业务动作和结果，例如“已检查 Amazon US 必填属性”。工具名、原始 JSON、XML 和模型中间过程仅在“技术详情”中按需展开。

## 11. 首页内容要求

### 11.1 Hero

**标签**：AI 跨境上新 Agent  
**主标题**：从选品到上架，一键完成  
**副标题**：AI 帮你发现商品机会，补齐上架资料，生成主图、详情页与多语言 Listing，自动适配平台规则并完成后台发布。  
**主按钮**：开始一次智能上新  
**次按钮**：导入已有商品

### 11.2 证明内容

首页不使用模拟 Agent Trace 作为核心证明，而是展示一个真实 SKU 的闭环结果：

- 用时。
- 识别和补齐的商品字段。
- 发现并修复的阻断项。
- 最终发布平台和平台回执。

“高转化”不作为上架前的事实承诺；在没有真实经营数据前使用“面向转化优化”。

## 12. 非功能要求

- 任务超过 10 秒必须显示当前业务阶段，不允许轨迹已运行但主进度仍为 0%。
- 轮询或网络错误必须显示可理解的状态和重试操作，不允许无限期显示“加载中”。
- 模型、图像或连接器失败时必须标注降级结果，不得把占位内容当作真实产物。
- 用户编辑、确认和发布记录必须在页面刷新后保留。
- 生成内容与商品事实的关联校验必须可自动测试。

## 13. 发布计划

### Sprint 1：建立项目与事实层

- SKU 项目模型与状态机。
- 商品事实、来源和确认状态。
- 项目列表和项目详情骨架。
- 阻止未确认推断进入发布草稿。

### Sprint 2：打通草稿与发布闸口

- 准入诊断与三级检查结论。
- 草稿字段来源、编辑和复检。
- 发布快照与用户确认闸口。
- 业务化进度与错误状态。

### Sprint 3：闭合发布与失败重试

- mock 后台发布回执。
- 平台错误到草稿字段的映射。
- 修复、复检、新版本和重试。
- 端到端演示与回归测试。

### P1：扩展选品与多平台

- 可解释的 AI 选品入口。
- 从候选品创建 SKU 项目。
- 将 Amazon US 深度路径复制至其他平台和站点。
- 批量审阅和批量发布。

## 14. 演示验收剧本

MVP 必须稳定演示以下路径：

1. 用户上传便携榨汁杯图片和一句卖点，选择 Amazon US。
2. AI 提取容量、重量、充电方式等事实，将品牌、材质、包装清单标记为缺失，不编造品牌。
3. 用户补充并确认商品档案。
4. 系统返回 Amazon US 准入结论，不混入欧盟 GPSR 要求。
5. 系统生成可编辑草稿，用户修改一处标题并看到即时复检。
6. 系统明确显示“已通过发布检查”，并列出仍需知情的警告。
7. 用户确认后发布至 mock 卖家后台，页面展示分步进度。
8. 系统返回 `listing_id` 和商品链接。
9. 另一次演示中注入属性错误，系统定位字段，用户修复后成功重试。

验收失败条件：

- 任意未确认的推断信息被直接发布。
- 存在阻断项时页面仍显示“合规通过”。
- 发布后无法说明提交的草稿版本。
- 发布失败后只能重新创建项目。
- 技术日志代替用户可理解的业务状态。

## 15. 待解决问题

1. MVP 商品事实字段是否按“通用字段 + 类目字段”动态组合？
2. 用户确认的最小粒度是单字段，还是允许对同一证据来源批量确认？
